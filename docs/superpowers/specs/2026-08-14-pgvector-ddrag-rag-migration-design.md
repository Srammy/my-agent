# MyAgent 迁移 DD_Rag document_chunks 与 PgVector 检索设计

## 1. 背景与目标

当前分支已经具备个人知识库的上传、Kafka 异步 ETL、Spring AI 文档解析、多模态 OCR/图片理解和 Elasticsearch 检索能力。本次将 DD_Rag 中已验证的单层文档 chunk 持久化和混合检索核心移植到当前分支，不保留当前分支原有的父子文档模型。

目标是形成以下链路：

```text
上传文档
  -> MySQL 保存文档与任务
  -> Kafka 异步投递
  -> 本地文件读取与 Spring AI 解析/OCR
  -> 清洗与结构感知单层 chunk 切分
  -> PostgreSQL document_chunks 持久化
  -> PgVector 向量化
  -> Elasticsearch 关键词索引
  -> 查询规划/改写
  -> ES 关键词召回 + PgVector 向量召回
  -> 应用层 RRF
  -> 连续 chunk 聚簇
  -> 邻居扩窗
  -> 证据等级控制
  -> Agent 基于证据回答并在末尾输出参考来源
```

## 2. 范围与明确不移植项

### 2.1 本期移植

- DD_Rag 的 `document_chunks` 数据模型、批量写入、按文档清理和按用户隔离查询。
- DD_Rag 的结构感知单层 chunk 切分、连续 chunk 聚簇和邻居扩窗。
- Spring AI PgVector 向量存储与向量检索适配器。
- ES 关键词检索适配器。
- 应用层 RRF，RRF 常数默认为 60，不依赖 Elasticsearch 内置 RRF。
- 查询规划/改写：DIRECT、REWRITE、DECOMPOSE，最多 3 个检索查询；规划失败自动回退原问题。
- 连续 chunk 聚簇、每个聚簇前后邻居扩窗，以及证据等级 SUFFICIENT/PARTIAL/WEAK/NONE。
- 证据不足或相关性低于 env 阈值时拒答，不让 Agent 使用知识库外部知识补答。

### 2.2 明确不移植

- DD_Rag 的 MinIO/对象存储读取。当前分支继续从本地知识库存储目录读取上传文件。
- DD_Rag 的 Spring Event 异步机制。当前分支继续使用 Kafka、outbox relay、consumer retry 和 DLT。
- DD_Rag 的 group/group membership 授权模型。当前分支继续使用 `userId` 作为个人知识库的隔离边界。
- Elasticsearch 内置 RRF 或 Elasticsearch 向量召回。ES 子索引只负责关键词召回，向量召回由 PgVector 完成。

## 3. 关键架构决策

### 3.1 数据库职责

保留 MySQL 作为 MyAgent 的业务数据库，保存用户、会话、知识库文档元数据和 Kafka 任务状态。新增 PostgreSQL Docker 服务，专门保存 chunk 和 PgVector 数据。

| 数据 | 存储 | 说明 |
|---|---|---|
| 文档元数据、状态、上传任务 | MySQL | 现有 `knowledge_documents`、`knowledge_document_jobs` |
| 文档原文临时文件 | MyAgent 本地 volume | 现有 `knowledge_data`，由 Kafka ETL 消费后清理 |
| 文档 chunk | PostgreSQL `document_chunks` | 可回查、可扩窗、可重建 ES |
| chunk 向量 | PostgreSQL `vector_store` | Spring AI PgVector 管理，metadata 含 userId/documentId/chunkId |
| 关键词索引 | Elasticsearch 8.x | 只索引单层 chunk，检索命中后从 PostgreSQL 回查扩窗上下文 |

### 3.2 ID 适配

DD_Rag 使用 Long 类型的 document/group ID；当前分支的文档 ID 是 `doc_...` 字符串，用户 ID 是 Long。因此迁移后的 `document_chunks.document_id` 使用 `varchar(64)`，`user_id` 使用 bigint，chunk 主键使用 PostgreSQL identity bigint。

当前分支不存在 group 维度，所有 `document_chunks`、PgVector metadata 和 ES 文档都必须包含 `user_id`。任何只按 documentId 查询的内部方法都不作为外部检索授权入口。

### 3.3 切分模型

本期采用 DD_Rag 的单层结构感知 chunk 模型，不保留父文档、子文档、parentId 或 childId：

- 按标题、段落、句子和 token/字符预算切分为连续 chunk。
- `chunk_index` 是同一文档内从 0 开始的稳定顺序号。
- `chunk_id` 使用稳定规则生成，例如 `${documentId}:${chunkIndex}`，作为 PostgreSQL、PgVector 和 ES 的统一合并键。
- metadata JSON 保存 pageNumber、sectionPath、charStart、charEnd 等结构信息。
- 检索命中后，按同一文档的连续 chunk 聚簇，并通过前后邻居扩窗补足上下文。

切分目标、最大长度和 overlap 采用 DD_Rag 的结构感知策略，并通过当前知识库配置暴露；不得改变现有 OCR、图片理解和表格 Markdown 抽取流程。

## 4. 入库流程

### 4.1 Kafka 消费流程

`KnowledgeDocumentKafkaConsumer` 仍然是唯一异步入口，消费消息后调用 ETL processor：

1. 按 `(userId, documentId)` 查询并校验 MySQL 文档所有权。
2. 清理该文档旧的 PostgreSQL chunks、PgVector 向量和旧 ES chunk 索引记录。
3. 从本地 storage 读取原文件。
4. 使用当前 Spring AI reader 完成文本解析、OCR、图片内容理解和表格结构化抽取。
5. 使用结构感知单层切分，生成连续 chunk。
6. 批量写入 PostgreSQL `document_chunks`。
7. 使用配置的 `EmbeddingModel` 批量生成 chunk 向量，写入 PgVector；metadata 至少包括 `userId`、`documentId`、`chunkId`、`chunkIndex`、`sourceFilename`。
8. 从同一批 chunk 写入 ES 关键词索引。
9. 只有 PostgreSQL、PgVector 和 ES 全部成功后，MySQL 文档才更新为 READY，并更新 `chunkCount`；历史 `parentCount`/`childCount` 字段不再表达入库结构。
10. 成功后删除本地原文件。

### 4.2 失败与重试

- 任意阶段失败，清理本次文档的 PostgreSQL chunks、PgVector 向量和 ES 索引；不清理其他用户或其他文档。
- MySQL 文档保持 PROCESSING，Kafka 重试耗尽后由现有 DLT/失败处理逻辑设置 FAILED，并记录截断后的错误原因。
- retry 接口重新投递 Kafka 消息；处理开始时再次执行按 `(userId, documentId)` 的幂等清理。
- 不允许旧索引残留参与下一次检索，避免失败重试后出现重复 chunk 或旧版本答案。

## 5. PostgreSQL 数据模型

新增 Flyway PostgreSQL migration，至少包含：

```sql
create extension if not exists vector;

create table document_chunks (
  id bigint generated by default as identity primary key,
  user_id bigint not null,
  document_id varchar(64) not null,
  chunk_id varchar(160) not null,
  chunk_index integer not null,
  chunk_text text not null,
  chunk_summary text,
  char_start integer,
  char_end integer,
  metadata_json jsonb,
  created_at timestamp not null default current_timestamp,
  updated_at timestamp not null default current_timestamp,
  unique (user_id, document_id, chunk_index),
  unique (user_id, chunk_id)
);

create index idx_document_chunks_user_document
  on document_chunks(user_id, document_id, chunk_index);
```

PgVector 的 `vector_store` 表由 Spring AI starter 初始化；其 metadata 必须保存用户和文档边界，并通过 metadata filter 限制 `userId`，不能只依赖相似度结果再做内存过滤。

MySQL 的 `knowledge_documents` 增加 `chunk_count` 字段。现有 `parent_count` 和 `child_count` 字段仅为旧数据兼容保留，新入库流程不再依赖其含义，接口和页面改为展示 `chunkCount`。

## 6. 混合检索流程

### 6.1 查询规划/改写

新增当前分支可用的 `QueryPlanningService`：

- 输入：当前用户 ID、原始问题。
- 输出：DIRECT、REWRITE 或 DECOMPOSE，以及最多 3 个查询字符串。
- 规划模型调用失败、结构化输出非法或用户上下文不可用时，返回 DIRECT 原问题。
- 查询规划只生成检索表达，不直接回答问题。

### 6.2 双通道召回

对每个 planned query 并行或顺序执行两路召回：

- ES 关键词：过滤 `userId`、READY 状态和可选 documentIds；使用文件名/正文的 match_phrase 与 match 组合，返回 chunkId、documentId、chunkIndex、文件名和关键词分数。
- PgVector：使用 Spring AI `VectorStore.similaritySearch`，metadata filter 强制包含 `userId`，返回同样的 chunk 标识和向量分数。

两路都取配置的 channel topK（默认 50），最终证据数量使用知识库检索 `topK` 配置。

### 6.3 应用层 RRF

以 `chunkId` 作为候选合并键，对每一路按排名计算：

```text
rrf(channel, chunk) += 1 / (60 + rank)
```

同一 chunk 被多路或多个 planned query 命中时累加分数，保留 vectorScore、keywordScore、hybridScore 和 retrievalSource（VECTOR/KEYWORD/BOTH）。按 hybridScore 降序得到候选。

### 6.4 连续 chunk 聚簇与邻居扩窗

1. 先按 documentId 分组。
2. 同一文档内按 chunkIndex 升序，把连续的候选合并为一个 cluster。
3. 以 cluster 最高分 chunk 作为 primary。
4. 通过 PostgreSQL 按 `(userId, documentId)` 查询 READY chunk，向 cluster 前后各扩展 `neighborWindow` 个 chunk，默认 1。
5. 拼接扩窗内容形成 evidence document，并记录 primary、起止 chunk、来源和分数元数据。

聚簇和扩窗只允许在同一个 userId + documentId 范围内发生，不能跨用户或跨文档拼接。

### 6.5 证据等级与拒答

证据等级沿用 DD_Rag：

- NONE：没有有效证据，坚决拒答。
- WEAK：只有单路或单条弱证据，只能谨慎回答并明确依据有限。
- PARTIAL：证据覆盖不完整，只回答明确支持的部分。
- SUFFICIENT：多条证据或双路命中，允许正常回答，但不能超出证据推断。

此外，应用层对最终 hybridScore 执行 `KNOWLEDGE_RETRIEVAL_MIN_RRF_SCORE` 阈值拦截。低于阈值的结果全部丢弃；阈值配置为 0 时表示关闭该分数拦截，但 NONE 仍然必须拒答。

## 7. Agent 回答约束

知识库模式继续使用普通 Agent 能力，但回答 prompt 必须包含：

- 只能依据检索 evidence 回答。
- evidence 不支持的内容必须拒答或说明无法确定。
- 必须在回答最后输出“参考来源”段落，列出文件名、页码或 chunk 来源。
- 不得把查询规划结果、RRF 分数、内部 userId 等实现细节输出给用户。

普通对话模式不触发上述知识库检索约束。左侧会话模式仍由 MySQL 会话记录区分。

## 8. Docker 与配置

新增 PostgreSQL 服务，使用带 pgvector 的镜像并持久化 volume；MySQL、Redis、Kafka、ES、backend、frontend 保持现有 Docker Compose 结构。

新增 env 配置：

```dotenv
KNOWLEDGE_POSTGRES_HOST=postgres
KNOWLEDGE_POSTGRES_PORT=5432
KNOWLEDGE_POSTGRES_DATABASE=myagent_knowledge
KNOWLEDGE_POSTGRES_USERNAME=knowledge
KNOWLEDGE_POSTGRES_PASSWORD=change-me
KNOWLEDGE_PGVECTOR_TABLE=vector_store
KNOWLEDGE_PGVECTOR_DIMENSIONS=1024
KNOWLEDGE_RETRIEVAL_CHANNEL_TOP_K=50
KNOWLEDGE_RETRIEVAL_RRF_K=60
KNOWLEDGE_RETRIEVAL_NEIGHBOR_WINDOW=1
KNOWLEDGE_QUERY_PLANNING_ENABLED=true
KNOWLEDGE_QUERY_PLANNING_MAX_QUERIES=3
```

Embedding 模型仍由 `KNOWLEDGE_EMBEDDING_MODEL` 和相关配置选择；OCR/多模态模型仍由 `KNOWLEDGE_MULTIMODAL_MODEL` 选择。PgVector 维度必须和 embedding 模型输出维度一致，应用启动时校验配置。

## 9. 迁移与兼容策略

- 不删除现有 Docker volume，不自动清理已有用户数据。
- 新增 PostgreSQL schema 后，已有文档不会自动拥有 chunks/vector；需要通过“重试/重新解析”重新构建。
- 新版 ES chunk index 使用新的 env index 名称或在停机窗口内显式重建，避免旧的 parent/child 和 dense_vector mapping 与新的单层关键词 mapping 混用。
- 迁移期间查询只使用 READY 且在新 PostgreSQL 与 ES/PgVector 中完整存在的文档；不完整文档必须视为不可检索。

## 10. 验证标准

必须覆盖以下测试：

1. 同一用户多文档：关键词和向量召回能合并为同一 chunk，RRF 排序稳定。
2. 两个用户拥有相同文档内容：用户 A 查询不能命中用户 B 的 PostgreSQL chunk、PgVector 向量或 ES 文档。
3. retry：旧 chunks/vector/ES 记录先清理，失败后不留下可检索半成品，再次成功后只有一份数据。
4. 查询规划失败：自动回退 DIRECT，不阻断检索。
5. 连续 chunk 聚簇与邻居扩窗：只扩展同一用户、同一文档、相邻 chunk。
6. 阈值拦截：低于 `KNOWLEDGE_RETRIEVAL_MIN_RRF_SCORE` 时返回空证据并拒答。
7. NONE/WEAK/PARTIAL/SUFFICIENT 四种证据等级对应正确回答约束。
8. Docker 启动后 PostgreSQL pgvector、Kafka、ES、MySQL、backend 健康检查通过。

## 11. 非目标

- 不在本期引入 MinIO 或其他对象存储。
- 不在本期把 Kafka 改为 Spring Event。
- 不把整个 DD_Rag 的组权限、模型平台和 Agent 实现复制到 MyAgent。
- 不引入 Elasticsearch 内置 RRF。
- 不保留当前分支原有的父子文档切分、parent index、child index 或 parent/child 计数语义。

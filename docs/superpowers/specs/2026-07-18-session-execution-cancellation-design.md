# 会话执行取消设计

## 目标

用户删除会话时，必须停止该会话正在运行的 Agent 和后续工具执行。已完成的外部副作用不回滚。

系统以多实例部署为前提：删除请求与执行流可能位于不同后端实例。

## 非目标

- 不实现外部工具副作用回滚。
- 不改变手工上传 Skill、Skill 审批或普通会话创建行为。
- 不建设通用任务调度系统。

## 架构

新增 `SessionExecutionCoordinator`，由两部分组成：

- 每个实例的本地执行登记：保存 `userId + sessionId + executionId` 对应的取消句柄。
- Redis 协调状态：保存会话取消标记、活跃执行记录，并发布/订阅取消消息。

聊天流和工具确认恢复流在订阅时登记为执行；自然结束、异常结束、浏览器断开或取消时注销。

## 执行流程

1. 聊天或确认恢复开始前，检查 Redis 会话取消标记。
2. 未取消时，在 Redis 创建活跃执行记录并在本机登记取消句柄。
3. 启动 AgentScope 流。取消句柄调用 Reactive Streams 订阅的 `cancel()`。
4. 取消传播至 `Flux.using`，关闭 `HarnessAgent`，停止后续 Agent 与工具步骤。
5. 流结束时注销本地和 Redis 活跃记录。

删除与执行登记使用同一会话键协调：删除先写入取消标记。已经通过会话所有权校验、但尚未启动的流在登记前会看到该标记并拒绝启动。

## 删除流程

1. 校验会话归属。
2. 写入会话取消标记，阻止新执行。
3. 向 Redis 发布取消消息。
4. 每个实例收到消息后，取消本机匹配的所有执行流。
5. 删除请求轮询活跃执行记录，直到全部注销。
6. 全部停止后删除会话数据库记录并返回 204。

若在规定等待时间内仍有活跃记录，接口返回“取消仍在进行”，不删除会话记录。取消标记保持有效，用户可重试删除；该会话也不能启动新聊天或工具确认。

实例崩溃后，活跃执行记录依靠 TTL 自动过期。TTL 必须由运行中的执行定期续期，避免长时间模型调用被误认为已停止。

## 前端行为

- 聊天 store 为每个会话保存 `AbortController`。
- 用户点击删除时立即中止本地 NDJSON 请求，减少浏览器端等待。
- 页面在 DELETE 返回 204 后才移除会话和消息。
- DELETE 超时时保留会话和消息，显示“正在停止，请稍后重试”。

浏览器中止只是优化；服务端 Redis 协调才是停止的权威来源。

## 错误与并发

- 已取消或已删除的会话发起聊天/确认时返回冲突或未找到，不启动 Agent。
- 多个删除请求共用同一取消状态；不得重复启动或恢复 Agent。
- Agent 自然结束和失败都必须清理本地句柄与 Redis 活跃记录。
- 删除操作只保证停止未完成和后续步骤；无法撤销已经完成的外部副作用。

## 测试

- 本实例删除会取消运行中的聊天流和确认恢复流。
- Redis 取消消息可取消另一实例登记的流。
- 删除与新聊天并发时，新聊天不会启动。
- 活跃执行未结束时 DELETE 不返回成功、不删除会话。
- 活跃执行全部结束后 DELETE 删除会话。
- 前端仅在 DELETE 成功后清理 UI；超时保留会话并展示错误。
